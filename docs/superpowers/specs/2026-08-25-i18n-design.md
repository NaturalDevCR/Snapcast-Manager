# Internationalization (i18n) — design

Date: 2026-08-25
Source: `docs/superpowers/plans/2026-08-18-professional-hardening.md`, Stage
4, item 4.9: microcopy/i18n string extraction.

## Goal

Add EN/ES internationalization support to Snapcast-Manager's client, with
a real user-facing language switcher, and extract a representative first
slice of the app's hardcoded English strings to prove the pattern works
end-to-end. The user is Costa Rica-based and bilingual.

## Non-goals

- Not extracting every view's strings in one pass — this design and its
  implementation plan cover infrastructure plus a pilot set of views.
  The remaining ~15 views are follow-up work, tracked as separate,
  smaller SDD tasks after this plan ships (same shape as Task 32's
  app-wide aria-label sweep or Task 37's contrast sweep).
- Not translating server-emitted text. API error messages surfaced via
  `uiStore.showToast(err.message)` stay in English — i18n-ing the
  backend is materially larger, separate scope.
- Not adding any language beyond EN/ES.
- Not building a translation-management UI or external translation
  service integration — translation files are hand-maintained JSON,
  same as any other source file.

## Library & locale mechanics

`vue-i18n`, Composition API mode (`legacy: false`, `useI18n()`), matching
this app's existing all-`<script setup>` convention.

- Default locale: `navigator.language` matched against the two supported
  locales (`en`, `es`), falling back to `en` if neither matches.
- Override: persisted the same way theme preference already is — via
  `useUIStore()` → `localStorage`, so an explicit choice survives reloads
  independent of OS/browser settings. Follow `useUIStore()`'s existing
  theme-persistence code as the direct structural reference.
- `vue-i18n`'s built-in named interpolation and pluralization cover this
  app's many dynamic strings (e.g. the `:aria-label="\`Delete ${pipe.name}\`"`
  patterns built throughout Task 32) without extra tooling —
  `t('pipeSources.deleteAria', { name: pipe.name })`.

## Switcher UI

A small EN/ES toggle added to `Layout.vue`, positioned next to the
existing theme toggle, matching its visual affordance (not a dropdown —
two languages don't need one). Uses the same `useUIStore()`-backed
persistence as the theme toggle.

## File structure

```
client/src/locales/
  en/
    common.json       # buttons, nav labels, generic toast templates
    login.json
    setup.json
    onboarding.json
    layout.json        # nav labels, the switcher's own strings
    dashboard.json
  es/
    common.json
    login.json
    setup.json
    onboarding.json
    layout.json
    dashboard.json
```

One namespace file per view (matching the view's own name), plus a
`common.json` for cross-cutting strings shared across views. Mirrors
this app's per-view component structure — same "small, focused file"
principle this session's own view-decomposition work (Tasks 38-45)
already established. Future follow-up tasks extracting the remaining
~15 views each add one more `<view-name>.json` pair, not touch the
existing ones.

## Rollout scope for THIS implementation plan

Infrastructure (vue-i18n setup, locale detection/persistence, the
switcher) plus extraction of:
- `Login.vue`, `Setup.vue`, `Onboarding.vue` — the entire first-run/auth
  flow: small, self-contained, and the highest-visibility surface a new
  admin sees.
- `Layout.vue` — nav labels and the switcher itself.
- `Dashboard.vue` — the one complex, high-traffic view included in this
  pass, to prove the pattern holds up against real-world string density
  and dynamic content (not just simple static-copy views).

Every other view (`Routing.vue`, `PipeSources.vue`, `ServerConfig.vue`,
`Tools.vue`, `Security.vue`, `Watchdogs.vue`, `Logs.vue`,
`ClientDashboard.vue`, and the various extracted child components from
Tasks 38-46) stays in English for now, tracked as explicit follow-up
work once this plan ships.

## Testing

Existing Vitest smoke tests assert on literal English copy throughout.
To avoid a large, unrelated assertion-rewrite as a side effect of this
plan, the shared test-mounting helper(s) mount views with the i18n
plugin defaulting to locale `'en'` — every existing English-text
assertion keeps passing unchanged. New tests specific to this plan
cover: the switcher toggling to `'es'` and the expected Spanish text
appearing, locale persistence across a simulated reload, and the
`navigator.language`-based default-locale detection logic in isolation.

## Open questions / risks for the implementation plan to address

- Exact `vue-i18n` version/bundle (the full runtime vs. the
  smaller `vue-i18n/dist/vue-i18n.runtime.esm-bundler.js` build) and
  whether Vite needs a config flag (`__VUE_I18N_FULL_INSTALL__` etc.) —
  a known `vue-i18n` + Vite integration detail to verify against the
  actual installed version, not assume from memory.
- Whether translation KEYS should be nested-by-section (mirroring each
  view's own visual sections) or flat-per-string — a call the
  implementation plan should make concretely with real examples from at
  least one pilot view (`Login.vue`, the smallest) rather than left
  abstract.
- Spanish translations themselves need to be genuinely correct
  Costa-Rica-appropriate Spanish, not machine-translated filler —
  flagged explicitly so whoever executes the plan treats the `es/*.json`
  content with real care, not placeholder text.
